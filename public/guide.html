u dont GRC me

A control-centric GRC product prototype. Controls are the system of record, and assets, frameworks, evidence, risk, integrations, and AI-agent decisions all map around each control. Build the control layer properly and audit evidence, risk, policy, and compliance compose off it — instead of being maintained five separate times.

▶ Open the live app → Start on the Command Center, then pick a control and follow the assets, framework mappings, evidence, and FAIR loss exposure that hang off it.

What it does

The app opens on a Command Center — median annualized loss exposure, control health, pending AI approvals, and evidence freshness across the top, with FAIR loss exposure broken out per control underneath. Every number on that screen resolves back to a control:

  • Loss exposure is a FAIR figure attached to a control.
  • Evidence freshness is measured against the control the evidence proves.
  • Framework coverage is a mapping from a requirement onto the same control.

Assets, frameworks, evidence, risks, integrations, and AI-agent decisions are all views onto the control they attach to — not separate registers you reconcile by hand.

The thesis

Most GRC tooling keeps a control inventory, a risk register, an evidence library, a policy set, and a framework crosswalk as five parallel things, and spends its effort keeping them in agreement. This inverts that: the control is the primary object, and everything else is a projection of it. Get the control layer right once and the rest composes, rather than drifting apart between audits.

When and where to use it

Use it to

  • See a control-first GRC surface where risk, evidence, and coverage are all anchored to one control object.
  • Read loss exposure as a FAIR number per control rather than a heat-map color.
  • Explore what "controls as the system of record" looks like as a product, not a slide.

Do not expect

  • A place to enter your own data. The hosted app is read-only — it serves a seeded governance snapshot, not a live tenant.
  • Production numbers. The figures are illustrative seed data for the prototype.
  • The engineering builds — those are the CLI and control-plane tools; this is the product surface that sits on the same control-first thesis.

How it's built

LayerChoice
UIA React / Vite single-page app, published to GitHub Pages (and mirrored via CloudFront).
APIA read-only Governance API on an AWS Lambda function URL, backed by DynamoDB for the governance snapshot.
AccessThe CloudFront origin is a private S3 bucket with public access blocked, reachable only through the distribution.
Localnpm run dev:full starts the Vite UI plus a SQLite-backed API for full local mode.
The hosted API stays read-only from the public app until authenticated mutation workflows are added. Endpoint hostnames are supplied at build time rather than committed.

Honest limits

  • This is a product prototype: the hosted experience is read-only and runs on seeded data.
  • Mutation flows (editing controls, approving AI decisions for real) are scaffolded for local mode, not exposed on the public app.
